# 踩坑记录

> 每条记录包含：现象、根因、解决方案、沉淀出的测试/规范。按时间倒序。

## 2026-11-06

### 1. GLM 返回的 JSON 被 markdown 围栏包裹

- **现象**：要求模型只输出 JSON，实际返回 `` ```json\n{...}\n``` ``。
- **根因**：聊天模型的格式化倾向，即使 system prompt 强调纯 JSON 也可能加围栏。
- **解决**：LLM 客户端统一做围栏剥离 + 容错解析（`llm.py` 中实现），不依赖 prompt 约束。
- **沉淀**：AI 管线禁止直接 `json.loads` 模型原文，必须走统一提取函数并对失败重试。

### 2. 替代表引用了不在白名单的食材名

- **现象**：`test_substitution_targets_known` 失败，如 `蒜`、`小葱`、`芝士`、`黄酒` 等口语名不是 canonical。
- **根因**：编写替代表时使用了口语短名，而 `is_known` 只认 canonical 集合。
- **解决**：逐一改为 canonical（大蒜、洋葱、猪肉等），缺失的 canonical（姜粉、蒜粉、白酒、白醋、椰浆、面包糠、四季豆、圣女果等）补入目录。
- **沉淀**：新增测试强制替代表的源头与目标都必须在白名单内，防止再次漂移。

### 3. 同义词一对多冲突

- **现象**：`豉油` 同时出现在 `酱油` 和 `蒸鱼豉油` 的同义词中；`粟米` 同时指向玉米和小米。
- **根因**：方言同义词在不同条目下重复维护。
- **解决**：`蒸鱼豉油` 同义词改为 `蒸鱼酱油`；玉米去掉 `粟米` 改用 `苞谷`。
- **沉淀**：`test_synonyms_are_unambiguous` 保证任意名称只能映射到一个 canonical。

### 4. 验收指标驱动的分类边界重构（重要设计决策）

- **现象**：初版 Cook Now 允许缺 1 样，真实查询里零缺失占比只有 25%–50%，达不到“≥60% 零缺失”的验收指标。
- **根因**：产品文档对 Cook Now（0~1）和 Almost（1~3）的边界在“1”处重叠；而剩余的 1 缺失项其实是真实主食材（苦瓜、紫菜、方便面），本应走替代方案。
- **解决**：
  1. 先引入 `PANTRY_STAPLES` 家常调料常备集合，盐/油/糖等琐碎调料不再算缺失；
  2. 再把 Cook Now 收敛为严格 0 缺失，1–3 缺失全部归入 Almost There 并挂替代建议。
- **沉淀**：新增验收测试，断言所有 Cook Now 匹配零缺失；决策理由写入本文件，避免后续反复。

### 5. 策展规格误用同义词当 canonical

- **现象**：菜谱规格里写 `葱花`、`青菜`、`腊肠`，构建校验报“不在白名单”。
- **根因**：这些是同义词（canonical 分别是小葱、小白菜、香肠），规格层约定只用 canonical。
- **解决**：食材元组统一改为 canonical；步骤正文里的自然语言不受影响。
- **沉淀**：约定“数据规格只用 canonical，同义词只存在于目录层”，并由构建期校验强制。

### 6. 环境工具链初始状态

- **现象**：git 不在 PATH；Python 无 requests/openai/pytest。
- **解决**：git 使用绝对路径 `C:\Program Files\Git\cmd\git.exe`；pip 安装 pytest；运行时坚持只用标准库（urllib），降低部署依赖。

### 7. 结果页三桶空白：vocab 字段名单复数不一致

- **现象**：首页点选、跳转、`#selection-summary` 都正常，但 `#buckets` 的 innerHTML 长度为 0，且一度无控制台报错。
- **根因**：`vocab.json` 导出的难度字段是 `difficulties`（复数），而 `page-result.js` 写成了 `CMF.data.vocab.difficulty.map(...)`（单数），在 `start()` 里 `render()` 之前就对 `undefined` 调 `.map` 抛异常，导致 `render()` 根本没执行。
- **排查弯路**：bu.js 运行在隔离执行环境，能共享 DOM 但访问不到页面 `window` 变量（直接引用 `CMF` 报 not defined），无法直接读页面状态；浏览器还会缓存旧脚本，一度掩盖了修复。最终靠在 `render` 外包 try/catch、换新端口、逐行核对字段名定位。
- **解决**：字段名改为 `vocab.difficulties`；并在所有页面加内联 emoji favicon 消除 404。
- **沉淀**：约定前端读取导出 JSON 前先核对 build.py 的实际键名；本地实测用独立端口规避缓存；新增前端字段需在测试/文档中登记。

### 8. 安全提示被逐字符拆成竖排（重要数据校验坑）

- **现象**：AI 卡片页的安全提示一字一行竖排显示，如“注意不要炒糊”变成 6 个单字 notice。
- **根因**：模型有时把 `risks` 返回成字符串而非数组，`for risk in payload.get("risks")` 直接对字符串迭代，Python 逐字符遍历，把每个字当成一条独立 safety note；`steps`/`cookware` 等列表字段也有同样隐患。
- **解决**：
  1. 新增 `_as_list()` 标量转列表辅助函数，字符串一律包成单元素列表，对 methods/tags/risks/steps/cookware 统一应用；
  2. 过滤“无/无风险/暂无”等空含义风险词；
  3. 写 `repair_safety_notes()` 数据迁移，把历史缓存里连续单字条目合并回整句，并提供 `python run.py repair` 命令。
- **沉淀**：`tests/test_batch.py` 覆盖 `_as_list` 与单字合并/空词过滤；确立“凡是模型给的列表字段，先 `_as_list` 再迭代”的硬规范。

### 9. 全量变体 315 次调用过慢，范围策略调整

- **现象**：64 道菜 × 7 种变体 = 315 次 API 调用，实测每小时仅推进约 100 项，全量需数小时，性价比低。
- **根因**：批处理按“每道菜全 7 种”顺序跑，大量变体内容同质化；前期未评估调用总量与耗时。
- **解决**：停止全量，改为“所有菜谱都有最常用的懒人版（64 项）+ 前 8 道菜保留完整 7 种”，共 109 个变体；断点续跑保证已生成内容不浪费。
- **沉淀**：批处理前先估算调用总量并按用户价值排序；先保证覆盖广度（每道菜至少一个可用按钮），再追求种类深度。

### 10. 模型把方法名塞进标签、把“勾芡/撕”当烹饪方法

- **现象**：部分懒人版校验失败——标签出现“凉菜/凉拌”（实为方法概念），方法出现“勾芡”“撕”（备菜/增稠动作而非受控烹饪方法）。
- **根因**：模型对“方法/标签”的边界理解不稳定，且会输出受控词表外的近义动作词；带反馈重试也未必一次纠正。
- **解决**：
  1. 标签归一化后过滤掉属于 `COOKING_METHODS` 的值，方法名不允许出现在标签里；
  2. 方法别名补“勾芡→煮”“撕→凉拌”，把近义动作映射到受控方法；
  3. 变体提示词强制差异化标题（如“懒人版XX”），并写 `repair_variant_title` 给历史数据补后缀。
- **沉淀**：`tests/test_batch.py` 增加变体标题修复用例；受控词表外的模型用词优先走“别名映射 + 错位字段过滤”，而非简单失败。

### 11. 新增批次与历史菜谱标题撞名

- **现象**：第 4 批里麻婆豆腐、宫保鸡丁、紫菜蛋花汤、冬瓜排骨汤与早期菜谱同名，连带懒人版变体标题也重复。
- **根因**：写新批次时只核对了 id，没有跨批次核对标题；而单菜谱校验无法发现跨记录的标题重复。
- **解决**：把第 4 批同名菜改为差异化标题（川味麻婆豆腐、家常宫保鸡丁、简易紫菜蛋花汤、清炖冬瓜排骨汤），并同步修正对应变体标题。
- **沉淀**：新增 `test_curated_titles_are_unique`，在构建期强制基础菜谱标题唯一；数据质量审计同时检查“基础内部”和“AI 与基础”两类重复。

### 12. 双实现分歧：JS 把零交集菜谱塞进 Almost（跨语言一致性坑）

- **现象**：同一份查询，Python 检索与前端 JS 结果不一致。例如只选「西瓜」，Python 返回空（没有菜用西瓜），JS 却在 Almost 桶里列出 50 多道与西瓜毫无关系的菜。
- **根因**：Python 侧只把“与所选食材至少有 1 样交集”的菜谱当候选；JS 侧对所有菜谱逐一评估，只要缺失数 ≤3 就归入 Almost，缺少候选剪枝这一步。
- **排查方法**：用 Node 写一致性 harness（`tests/consistency/node_harness.js`），加载真实前端 `search.js`，对 400 个随机查询分别跑 Python 与 JS，逐桶、逐排序、逐缺失列表比对，一次暴露全部分歧。
- **解决**：JS 检索循环里对 `matched.length === 0` 的菜谱直接跳过，与 Python 候选剪枝对齐。
- **沉淀**：`tests/test_consistency.py` 固化双实现 400 查询一致性，任何一侧改了检索逻辑都必须保持对齐；确立“双实现必须有跨语言一致性测试”的规范。

### 13. 模型用词落在受控词表外导致整批零星失败（别名覆盖坑）

- **现象**：低卡/空气炸锅批处理出现零星校验失败——方法「焯水」、标签「午餐/海鲜」、食材「油/姜片/清水」被判未知。
- **根因**：别名表只覆盖了部分近义形（有「焯」无「焯水」，生姜有「姜」无「姜片」），且目录里根本没有「水/清水」这一通用烹饪介质。
- **解决**：
  1. 方法别名补「焯水/汆/汆烫→煮」，标签别名补「午餐→一人食」，新增合法标签「海鲜」；
  2. 食材补同义词「姜片→生姜」「油→食用油」，并新增「清水」条目（同义词 水/白开水/饮用水），纳入 `PANTRY_STAPLES`（水普遍可得，不阻断分类）；
  3. 重跑失败项，7 项全部补齐，低卡/空气炸锅均达到 80/80 全覆盖。
- **沉淀**：模型近义用词优先扩别名/补通用条目，而非让整道菜失败；`failures.json` 保留历史失败便于定向重跑，重跑只生成缺失项、不重复调用。

### 14. 扩到 100 道菜后一致性测试“假失败”：harness 读的是旧站点

- **现象**：第五批 20 道菜加完、`run.py data` 后，一致性测试报 202 处分歧，且全是“Python 有 r081+、JS 没有”。
- **根因**：Node harness 从 `site/data/recipes.json` 读数据，而新增批次只更新了 `base_recipes.jsonl`，尚未 `build`，导致 JS 侧仍是 80 道菜、Python 侧已是 100 道，并非检索逻辑分歧。
- **解决**：先 `python run.py build` 让站点同步到 100 道，再跑一致性测试即通过。
- **沉淀**：约定“改了数据/词表后，先 build 再跑依赖 site 的测试”；一致性测试的失败要先区分“数据版本不一致”与“真实逻辑分歧”。

### 15. 夏日饮品/冷藏类 AI 输出的词表缺口与 ideas 标量问题

- **现象**：r097（冰镇绿豆汤）的懒人版/空气炸锅版反复失败——方法「冷藏」、标签「清凉解暑/夏日饮品」未知；r083 的 ideas 因“字段格式或数量不符”失败。
- **根因**：受控词表缺少“冷藏/免开火”这一冷处理动作和夏日饮品标签；ideas 解析要求严格 list，模型偶发返回标量或不足 3 项。
- **解决**：方法别名补「冷藏→免开火」，新增标签「夏日饮品」并把「清凉解暑」映射到它；ideas 改用 `_as_list` 容错后再校验数量，重跑全部补齐。
- **沉淀**：新增冷处理/饮品等新品类时同步扩词表；所有“模型给的列表”统一 `_as_list`，ideas 也不例外。

### 16. 家常替代版标签“家常菜/家常/晚餐”落在词表外

- **现象**：批量补 substitute 变体时，r012/r013 经多次重试仍失败，校验报“未知标签：家常菜/家常/晚餐”。
- **根因**：受控标签集没有“家常菜/晚餐”这类日常用语，模型在“家常替代”语境下高频产出它们；直接扩词表会让标签膨胀。
- **解决**：不扩词表，改在 `TAG_ALIASES` 加映射——家常菜/家常→下饭、晚餐→一人食（与既有“午餐→一人食”一致），重跑后 2 项全部成功。
- **沉淀**：词表保持封闭，模型漂移优先用别名收敛；新增别名后重跑失败项，`audit` 复核无残留。

### 17. 换做法变体把“搅拌机/破壁机”当烹饪方法

- **现象**：批量补 method 变体时，r017 多次重试失败，报“未知烹饪方式：搅拌机”。
- **根因**：METHOD_ALIASES 已有“搅拌/搅打”但没有带“机”的名词形式；模型在描述料理机操作时直接输出“搅拌机”。
- **解决**：METHOD_ALIASES 补“搅拌机/破壁机→免开火”，重跑成功；method 变体扩到前 20 道菜，变体总数 353。
- **沉淀**：别名要同时覆盖动词与名词形态；每类新变体批量后先看 failures，再统一补别名重跑。

### 18. 融合变体高频产出标签“融合菜/融合”，需要正式标签而非别名

- **现象**：批量补 fusion 时 7 项失败，全部报“未知标签：融合菜/融合”；同时发现首批 fusion 实际有缺口（r005/r007/r008 早先就失败未补）。
- **根因**：受控标签集没有“融合”这一类，而 fusion 是 7 种核心变体之一，没有合适的既有标签可映射。
- **解决**：正式新增标签“融合菜”，并把“融合”作为别名映射到它；重跑后 7 项全部成功，前 20 道菜实现全 7 种变体覆盖，总数 380。
- **沉淀**：区分“模型漂移”（用别名收敛）与“真实品类缺口”（正式扩词表）；批量统计要以实际缓存为准，不能只信历史总结。

### 19. 变体标题被重复加前缀（“懒人版懒人番茄炒蛋”）

- **现象**：全 6 页回归时发现 30 个变体标题出现语义重复，如“懒人版懒人番茄炒蛋”“空气炸锅版空气炸锅番茄炒蛋”。
- **根因**：旧 `repair_variant_title` 只判断完整后缀“懒人版”是否出现；模型返回的“懒人番茄炒蛋”含根词“懒人”但不含完整后缀，于是又被前置一次后缀。
- **解决**：新增 `VARIANT_TITLE_MARKERS`（同时列出版本化后缀与根词），`clean_variant_title` 先把“前缀+带标记的剩余部分”折叠，再保证存在标记；审计同步改为接受任意标记。修复清理 30 个标题，新增 2 个测试，全量 80 通过。
- **沉淀**：字符串修复要同时考虑“缺标记”和“重复标记”两个方向；回归要真的逐页读渲染文本，不能只看用例绿。

### 20. 新增“茴香”与八角的同义词“茴香”撞名

- **现象**：加入蔬菜“茴香”后，同义词唯一性测试报“茴香 同时映射到 八角 和 茴香”。
- **根因**：北方方言把八角（star anise）也叫“茴香”，旧目录把“茴香”列为八角同义词；而茴香菜（fennel）是另一种食材。
- **解决**：八角同义词改为“大料/八角茴香”，移除会与蔬菜撞名的“茴香”，让“茴香”专指茴香菜；测试恢复通过。
- **沉淀**：新增 canonical 前先跑同义词唯一性检查；一物多名要优先保留标准名，避免占用另一食材的通用名。

### 21. 模型用“真实食材的不同叫法”反复触发白名单失败

- **现象**：全量补变体时，少数项反复失败，报错“目录外食材：水淀粉/鸡汤/罗勒叶/白吐司/肉桂粉”等。这些都是真实存在的食材，只是和目录里的标准名（淀粉/高汤/罗勒/吐司/桂皮）叫法不同。
- **根因**：白名单只认标准名与已登记同义词；模型对同一食材的表述（含“粉/叶/汤/水”等形态后缀）不断漂移，且每次重试可能换一个新词。
- **解决**：把高频漂移词批量登记为同义词，新增缺失的罗勒、高汤两条 canonical；同时让标签过滤丢弃误放进 tags 的食材名（如“腐竹”）。重跑后 756 变体全部补齐。
- **沉淀**：白名单失败要先区分“真编造”与“异名同物”；后者补同义词即可，且应顺手把标签/方法槽位的错位值一并过滤，减少无效重试。

### 22. 目录存在大量孤立食材，菜谱与目录覆盖脱节

- **现象**：审计时统计发现 229 个食材里有 96 个未被任何菜谱使用；剔除家常调料后仍有 63 个非调料孤立食材（如丝瓜、鳕鱼、螃蟹、猪肝、金枪鱼等）。
- **根因**：早期先扩目录再补菜谱，食材目录增长快于菜谱，部分条目从未被任何策展或 AI 卡片引用。
- **解决**：以孤立食材为目标设计第八批 15 道菜（r121–r135），每道菜至少消费一个孤儿；缺失的皮蛋用咸鸭蛋替代，避免为单道菜硬加目录。
- **沉淀**：定期跑“食材使用率”检查，把孤立食材作为下一批菜谱的设计输入，让目录与菜谱保持同步增长。

### 23. leftover 变体把“剩菜”当作食材写进食材清单

- **现象**：`r126:leftover` 反复失败，报错“目录外食材：剩菜”。模型把提示词里的“假设这是剩菜”直接当成一个食材名。
- **根因**：leftover 提示词只说“假设这是剩菜”，没有明确禁止泛指词，模型便把“剩菜”作为占位食材输出。
- **解决**：改写提示词，要求食材必须写原菜谱真实食材或新加入的具体食材，明确禁止“剩菜”这种泛指词；同时新增芝麻 canonical、补金枪鱼罐头/黑醋等同义，4 个失败项重跑全部恢复。
- **沉淀**：提示词里出现的抽象概念（剩菜/适量/少许）容易被模型误当成枚举值；涉及白名单的槽位，要在提示词里显式给出“禁止词”和“应该写什么”。

### 24. 无头环境剪贴板写入失败：Document is not focused

- **现象**：用 `element.click()` 程序化触发“复制采购清单”，按钮始终不显示“已复制”；`navigator.clipboard.writeText` 报错 `Document is not focused`，`execCommand('copy')` 也返回 false。
- **根因**：自动化环境里 `document.hasFocus()` 为 false，剪贴板 API 要求文档聚焦；并非功能本身缺陷。真实用户点击会先聚焦文档。
- **解决**：在 ui.js 增加通用 `CMF.copyText`，优先用 Clipboard API，失败时回退到隐藏 textarea + `execCommand`；用真实 ref 点击（而非 JS `.click()`）验证，聚焦后复制成功并显示“✓ 已复制”。
- **沉淀**：测试涉及剪贴板/焦点的能力时，用真实点击聚焦再断言；同时任何复制入口都应带 execCommand 兜底，不能只依赖 Clipboard API。

### 25. 新 canonical 与既有同义词撞名（荷兰豆）

- **现象**：第十二批把「荷兰豆」作为新食材加入，构建时发现它早被登记为「豌豆」的同义词。
- **根因**：新增 canonical 前未先核对它是否已作为其他食材的别名存在，一物两名会造成归一化歧义。
- **解决**：先从「豌豆」同义词移除「荷兰豆」，再把它独立为 canonical；同义词唯一性检查随之通过。
- **沉淀**：新增 canonical 前先在整个目录检索该名称，确认它既不是 canonical 也不是任何食材的同义词。

### 26. 换做法变体把「冰箱冷藏」写进标签

- **现象**：`r195:method` 多次重试失败，报「未知标签：冰箱冷藏」。
- **根因**：这是一道免开火水果杯，模型把「放冰箱冷藏」这一处理动作当成标签输出；它本质是方法而非标签。
- **解决**：在 `TAG_ALIASES` 加「冰箱冷藏→免开火」，归一后产出的「免开火」属于方法，会被标签过滤逻辑自动剔除，重跑成功。
- **沉淀**：误放进标签槽位的方法类词，用别名映射到方法再过滤，比硬扩标签集更干净。

### 27. 半成品功能只改 UI 不接引用链，导致已有弹窗整体崩溃

- **现象**：上一个会话中断后，工作区只剩 `web/js/pairings.js`（未跟踪）与 `web/js/ui.js` 两处改动；9 个 HTML 全都**没有引入**新脚本，CSS/SW/构建产物/测试也都没动。`ui.js` 的食材百科弹窗却无条件调用 `CMF.topPairings(name, 6)`，浏览器实测点击食材名会抛 `TypeError`，整个百科弹窗（原有功能）打不开。
- **根因**：新增 `window.CMF` 全局能力时只补了「实现 + 调用方」，漏掉引用链五件套；而且 `CMF.boots` 里写了 `if (CMF.buildPairingIndex)` 保护，制造了「已经兜底」的错觉，调用方却裸调。
- **解决**：9 个页面统一在 `ui.js` 之前引入 `pairings.js`；调用方也改为 `CMF.topPairings ? CMF.topPairings(...) : []`；补齐 CSS 样式、SW 预缓存、`site/` 重建与两层无头回归（纯逻辑 17 项 + 弹窗 DOM 13 项）。新增 pytest 断言每个 HTML 都引入脚本且顺序在 ui.js 之前。
- **沉淀**：新增全局脚本必须按「HTML 引入 → 调用方兜底 → CSS → 构建复制 → SW 预缓存 → 回归测试」逐项核对；跨文件半成品比缺失功能更危险，因为它会顺带打坏已有功能。断点续作先跑一次真实浏览器点击，不要只信测试全绿。

### 28. 共现频次把盐和食用油当成「经典搭配」

- **现象**：食材共现推荐跑出来，鸡蛋的 Top 搭配是「盐 8 / 食用油 6」，米饭是「盐 3 / 食用油 3」，调料霸榜，几乎看不出搭配语义。
- **根因**：家常调料出现在绝大多数菜里，纯频次统计天然把它们排在最前，属于典型的高频停用项污染。
- **解决**：`buildPairingIndex(recipes, opts)` 支持注入 `isStaple`（默认取 `CMF.isStaple`，即目录里的 `PANTRY_STAPLES`），`topPairings` 在生成结果时过滤常备调料；真实数据复测鸡蛋 Top 变为小葱/番茄/米饭/吐司/紫菜/虾仁。
- **沉淀**：任何基于共现/词频的推荐都要先剔除高频停用项；过滤条件做成可注入参数，无头测试才能脱离完整前端环境独立验证。顺手修了 comparator 相等返回 1、`limit=0` 被 `|| 6` 吞掉两个边界问题。

### 29. PWA 预缓存清单漏掉全部 JS

- **现象**：`sw.js` 的 `CORE_ASSETS` 只列 HTML/CSS/data，一个 js 都没有；装完 SW 立刻断网时，页面脚本尚未被 runtime 缓存，会 404，与「首次访问后离线可用」不符。
- **根因**：install 阶段只预缓存内容资产，脚本依赖 fetch 拦截的运行时缓存，而运行时缓存要求先成功访问过一次。
- **解决**：把 18 个 `js/*.js` 全部加入 `CORE_ASSETS`，并在 `test_build.py` 加断言：遍历 `web/js/*.js`，逐个校验出现在 SW 清单里。
- **沉淀**：新增静态资产要同步更新预缓存清单，并用测试把「目录文件 ⊆ 预缓存清单」锁住，避免以后再加脚本时重犯。

### 30. 百科弹窗「常见替代」显示 `[object Object]`

- **现象**：Playwright 实测截图里，鸡蛋百科弹窗的「常见替代」渲染成 `[object Object], [object Object]`，而详情页下方的替代方案表格却是正常的。
- **根因**：`catalog.json` 的 `substitutions` 值是 `{canonical, reason}` 对象数组；`page-recipe.js`（`s.canonical` / `s.reason`）与 `search.js`（整对象透传）都按对象处理，唯独 `ui.js` 用 `subs.join("、")` 当字符串数组拼接。
- **解决**：`ui.js` 按对象渲染成 `sub-chip`（名称 + 理由小字，兼容纯字符串），CSS 补 `.sub-grid/.sub-chip/.sub-reason`；弹窗 harness 增 3 项断言（不出现 `[object Object]`、出现「淀粉」、出现理由文本）。
- **沉淀**：同一份数据在不同调用方的结构假设要保持一致；模板字符串里直接 `join` 数组前先确认元素类型。这个 bug 全量单测全绿也发现不了，是浏览器截图实测抓到的——渲染层必须真的看一眼。

### 31. 每次构建都给 catalog.json 制造无意义 diff

- **现象**：连续两次 `run.py build`，`site/data/catalog.json` 的 `substitutions` 区块整体换序，约 185 行增删，但内容完全没变，提交里夹带大段噪声。
- **根因**：`export_catalog()` 用 `for canonical in cat.canonical_set()` 遍历 set；Python 字符串哈希随机化使跨进程迭代顺序不稳定，JSON 键顺序随之漂移。
- **解决**：改为 `for canonical in sorted(cat.canonical_set())`，输出确定性；`test_build.py` 断言 `list(substitutions) == sorted(substitutions)` 锁住。
- **沉淀**：任何写进版本库的生成文件都必须确定性输出，遍历 set/dict 前先 `sorted`；否则无法从 diff 里分辨「真的改了数据」和「只是又构建了一次」。

### 32. 连续构建随机报 WinError 1224 / OSError 22

- **现象**：`run.py build` 偶发失败，一次在 `shutil.copy2(html)` 报 `[WinError 1224] 请求的操作无法在使用用户映射区域打开的文件上执行`，另一次在 `site/sw.js` 的 `write_text` 报 `OSError: [Errno 22] Invalid argument`；单独重试同一操作立刻成功。
- **根因**：本地 `http.server` 预览、浏览器 Service Worker 或 IDE 文件索引会短暂持有/映射 `site/` 下的资产，构建直接覆盖就撞上瞬时占用；不是代码逻辑错误。
- **解决**：`copy_web_assets` 增加 `_retry`（4 次、50ms 递增退避），包住 `copytree` / `copy2` / SW 写入；新增单测模拟前两次抛 `OSError` 验证自愈。构建前仍建议先停掉本地预览服务。
- **沉淀**：Windows 上覆写「可能被别的进程读」的生成文件要默认加重试，不要把瞬时占用当成构建失败；配合第 31 条的确定性输出，构建才既可复现又不脆弱。

### 33. 「换一个」把同一道菜换回来

- **现象**：浏览器实测在启用「纯素 + 素食 + 花生过敏」的一周菜单里点晚餐「换一个」，14 行菜名一个都没变；harness 用 14 道菜的极小候选池复现同样结果。
- **根因**：`rerollMeal` 的 `usedTitles` 用 `weekMeals(days).filter(m => 不是目标餐)` 构造，**恰好把被替换的那道菜本身放回了候选池**。候选池刚好等于 14 道时，唯一「未使用」的选择就是原菜，于是静默「换」成同一道。
- **解决**：`usedTitles` 直接取全部已排菜（包含目标餐）；若严格饮食筛选让候选池耗尽，`pickRecipe` 返回 null 时退化为只排除当天两餐（保证当天不重复、且一定不是原菜），允许与其它天重样。harness 增加「极小池仍能换菜」「换后不与当天另一餐重复」两项断言。
- **沉淀**：任何「换一个 / 重抽」逻辑，排除集合必须包含当前值本身；候选池可能小于槽位数时要有明确的降级策略，否则按钮会假装在干活。

### 34. 新增三个全局模块，引用链一次都不能漏

- **现象**：阶段 24 一次新增 `nutrition.js`（重写）、`diets.js`、`share.js` 三个全局能力，涉及 9 个 HTML、SW 预缓存、调用方兜底和 CSS；任何一页漏引都会让该页某个按钮抛 `TypeError`。
- **根因**：与第 27 条同源，但这次是「一次性铺开多个模块」，人工逐页改更容易漏。
- **解决**：统一所有页面的脚本顺序 `store → catalog → search → nutrition → diets → 页面专属 → pairings → share → ui → page-*`；`sw.js` 的 `CORE_ASSETS` 补齐 20 个 JS；新增 `tests/test_reference_chain.py` 断言 9 页全部引入 5 个全局脚本、顺序正确、无重复引用、每个 src 文件存在、SW 覆盖所有脚本、新 UI 控件与 CSS 选择器齐全。
- **沉淀**：批量铺全局模块时，把「引用链」写成可执行断言而不是 Checklist；跨页结构统一（相同顺序）比每页按最小依赖裁剪更不易错，纯逻辑脚本多加载几十 KB 的代价可以忽略。

### 35. 家常单位换算太粗，把一盘菜算成 19 kcal

- **现象**：营养估算上线后，浏览器实测一周菜单出现「两餐合计 16 kcal/人」；排查发现 195 道菜里有 26 道每份低于 60 kcal，蒜蓉菠菜只有 19 kcal。
- **根因**：`UNIT_GRAMS` 用一套通用值套所有食材——「1 把菠菜」按 50 g（实际约 150 g）、「1 颗西兰花」按 10 g（那是圣女果/蒜瓣的量级）、「半个西瓜」按 50 g；另外人工策展菜谱把食用油当常备调料省略，炒菜因此完全不计油脂。
- **解决**：`nutrition.py` 增加食材级换算覆盖（叶菜把 150 g、整颗蔬菜 80 g / 西兰花 300 g、干辣椒把 10 g、半个西瓜 500 g 等），保留香菜 30 g 这类香草特例；`estimateNutrition` 对「做法含炒/煎/炸/烤/空气炸锅且食材里没有任何油脂来源」的菜按 10 g 食用油计入，并在 `lines` 与卡片说明里显式标注。修正后 < 30 kcal/份 的只剩 7 道白灼/凉拌/冰品，属于合理低热量。
- **沉淀**：估算模型上线前必须看真实数据的分布尾部（最小值、低于阈值的样本明细），只断言「> 0 且 < 3000」抓不到数量级错误；对「被数据省略的隐含项」要补偿且必须透明标注，不能悄悄加。

### 36. 切换口味偏好会清空过敏原档案

- **现象**：冰箱页点「素食」后，`cmf.prefs` 只剩 `{tags:["素食"]}`，先前设置的过敏原全部丢失。
- **根因**：`renderPrefs` 里直接 `CMF.setPrefs({ tags: [...] })` 覆盖整个对象；加入 `diets` 后 prefs 字段更多，这个写法会连带抹掉饮食偏好。
- **解决**：改为 `const next = CMF.getPrefs(); next.tags = ...; CMF.setPrefs(next);`；`store.js` 新增 `getDiets/setDiets/toggleDiet`，全部走 read-modify-write；`getPrefs` 用 `{tags:[],diets:[],...safe}` 给旧数据补默认值。harness 断言切换 diet 后 tags 与 allergens 仍在。
- **沉淀**：设置对象只增不减字段时，任何 setter 都必须读-改-写；给旧 localStorage 数据补默认值要放在 getter 里，分散在各页面兜底迟早会漏。

### 37. 校验 ICS 的 CRLF 被 Python 文本读取吃掉

- **现象**：浏览器下载 `.ics` 后用 `Path.read_text(encoding="utf-8")` 检查，`"\r\n" in text` 返回 False，一度以为日历导出换行格式错了。
- **根因**：Python 文本模式默认启用 universal newlines，会把 `\r\n` 归一成 `\n`；文件本身是合规的（Node harness 已断言 `!/(?<!\r)\n/`）。
- **解决**：改用 `read_bytes()` 检查 `b"\r\n"`，复测 14 个 VEVENT、UTC 时间戳、CRLF 全部正确。
- **沉淀**：校验二进制/协议级格式（CRLF、BOM、编码）一律按字节读；文本模式只能用来核对内容，不能用来核对换行约定。

### 38. localStorage 结构升级不能直接丢弃旧数据

- **现象**：一周菜单从「每天 1 道」升级为「每天午餐 + 晚餐」，旧用户浏览器里存的是 `{index, recipeId, title}`，直接按新结构渲染会得到空卡片或 `undefined`。
- **根因**：静态站点没有服务端迁移，localStorage 里的数据版本完全由前端解释。
- **解决**：`planner.js` 增加 `isLegacyWeek` / `migrateWeek` / `fillWeekMeals`：把旧菜保留为午餐、只补晚餐，已手工换过的菜不丢失；`weekMeals` 同时兼容新旧结构，`rerollDay` 保留为「换午餐」的兼容别名；页面检测到迁移时 toast 提示。浏览器实测注入 7 条旧数据后刷新，正确得到 14 餐且首日午餐仍是原来的番茄炒蛋。
- **沉淀**：纯前端持久化结构升级要「读时迁移 + 保留用户选择 + 兼容旧读取器」，不要靠清缓存；迁移路径必须有真实浏览器注入旧数据的回归。

### 39. QR 时序图案必须在定位图案之前画

- **现象**：自研二维码矩阵看着「像」二维码，但 OpenCV / ZXing 连定位都失败（`detect` 返回 False），一个字都解不出。
- **根因**：先画了三个 7×7 定位角，再画第 6 行 / 第 6 列时序图案；时序图案把定位角右边界和下边界的暗模块覆盖成亮模块，左上角变成 `#........` 而不是 `#.....#`，三个角的 1:1:3:1:1 特征被破坏。
- **解决**：按规范顺序改为「时序 → 定位角 → 对齐图案 → 格式/版本信息」，定位角覆盖时序（两者重叠处本来就一致）。
- **沉淀**：QR 的功能图案有严格覆盖顺序，交换两个看似独立的循环就会静默毁掉整张码；先让解码器能「找到」符号，再去查数据码字。

### 40. 对齐图案表按版本索引时，v1 必须留空位

- **现象**：修好定位角后 `detect` 成功，但 `decode` 仍返回空；与 segno 参考矩阵逐模块对比有 106 处差异，反解参考矩阵只得到 184 个数据位而不是 208 个。
- **根因**：`ALIGN_CENTERS` 写成 `[ [], [6,18], [6,22], ... ]`，索引 1（v1）误拿到 v2 的对齐中心，于是 v1 在 (18,18) 多画了一个 5×5 对齐图案，吃掉 24 个数据模块。
- **解决**：表改为索引 = 版本，索引 0 占位、索引 1 为 `[]`、v2 才是 `[6,18]`，并补齐到 v10；harness 断言 `v1.isFunction[16][16] === false`。
- **沉淀**：这类「索引从 1 开始」的规范表，宁可写成 `null` 占位 + 显式注释，也不要靠视觉对齐数组；用参考实现反解码字是定位这类偏移最快的方法。

### 41. 二维码结构自检全绿，也可能完全扫不出来

- **现象**：矩阵尺寸、定位角、格式 BCH、码字数量全部通过断言，但解码器仍解不出内容；换一个掩码又能解。
- **根因**：结构断言只证明「长得像」，不能证明 RS 纠错码字、交织顺序、掩码与数据位流一致；开发期踩的 39/40 两个 bug 都是结构自检覆盖不到的。
- **解决**：pytest 增加真实解码回归——Node 导出矩阵 → Pillow 渲染 PNG → `zxing-cpp` 解码并逐字比对；另外用 OpenCV 交叉验证，发现它对某些 v1+mask4 合法符号有假阴性（ZXing 全部正确），因此测试优先 ZXing、OpenCV 兜底并允许那一个已知误判。交付前还从**真实浏览器生成的 PNG** 里裁出二维码解码成功。
- **沉淀**：编码类功能必须用独立实现的解码器端到端验证，且至少两个解码器交叉；单测只能当第一道筛子。

### 42. 静态站点的「日历订阅」不是真文件，且容易被 SW 自己清掉

- **现象**：静态托管没有后端，`/calendar.ics` 必然 404；日历客户端拿到 404 会直接退订。
- **根因**：菜单存在每个用户自己的 localStorage，构建期无法生成固定 .ics；而 SW 的 `activate` 又会删除除 `CACHE_NAME` 之外的所有缓存。
- **解决**：页面把当前菜单的 ICS 写进专用缓存 `cmf-calendar-v1`，SW 对 `calendar.ics` 请求单独分支返回（未订阅时返回合法空 VCALENDAR + `text/calendar`）；`activate` 白名单保留该缓存；每次 `saveState` 后自动重发布。浏览器实测订阅后菜单从 4 周缩到 1 周，事件数 56 → 14，关闭订阅后返回 0 事件的合法空日历。
- **沉淀**：SW 里「虚拟端点 + Cache Storage」是静态站点做用户级订阅的可行解；清理缓存时务必把业务缓存列入白名单，并在 UI 里诚实说明需要公网 HTTPS 且 SW 已激活。

### 43. 跨周菜单的 index 是全局偏移，不是「星期几」

- **现象**：把 1 周扩成 4 周后，第 2 周的卡片若直接用 `WEEKDAY_LABELS[d.index]` 会数组越界，采购清单也无法按周归并。
- **根因**：`index` 语义从「本周第几天（0–6）」变成「距起始日的天数（0–27）」，所有派生量都要换算。
- **解决**：统一用 `index % 7` 取星期、`Math.floor(index / 7)` 取周次；`weekToICS` 的 `addDays(start, index)` 天然支持跨周，UID 因含日期仍唯一；`weekShopping` 给每个食材附 `weeks: [...]`；`weekToText` 按周分组输出。
- **沉淀**：扩大数据结构维度时，先列出所有「对索引做假设」的调用方（渲染、导出、聚合、迁移），逐个改成显式换算，并用多周 harness 锁住。

### 44. 「一键优化」把整份菜单洗牌，等于刷分加丢用户选择

- **现象**：初版 `optimizeMenu` 遍历所有 28 天、每天挑最高分替换，4 周平均分从 68 冲到 99，56 道菜全被换掉，用户手选的菜一个不剩。
- **根因**：优化目标只有「分数最大化」，没有约束改动范围，也没有区分「已经不错的天」。
- **解决**：只处理得分 < 70 的天、最多改 `ceil(天数/3)` 天，每天只替换一餐；实测 62 → 82 分、56 餐仅改 10 餐，且 harness 锁住「高分天不变 / 任何一天不下降 / 改动数上限」。
- **沉淀**：推荐/优化类功能要有「克制约束」，否则指标越好用户体验越差；优化结果必须可解释、可预期、保留人工选择。

### 45. 批量给 9 个页面插全局脚本，脚本要幂等且顺序要被测试锁住

- **现象**：一次新增 `balance.js` / `qrcode.js` 两个全局模块，手工改 9 个 HTML 容易漏页、重复插入或把 qrcode 放到 share 之后（分享图会静默没有二维码）。
- **根因**：项目没有打包器，模块加载完全依赖 `<script>` 顺序；页面专属脚本位置还各不相同。
- **解决**：用一次性幂等 Python 脚本按锚点插入（先检查是否已存在），插入后逐个打印脚本顺序复核；`test_reference_chain.py` 把 `GLOBAL_SCRIPTS` 扩成 7 项并断言顺序递增、SW 预缓存覆盖全部 22 个 JS、新控件与样式存在。
- **沉淀**：无构建链的静态项目，批量改动用幂等脚本而不是 9 次手改；引用链测试是唯一能防止「漏一个页面」的护栏。

### 46. 同步二维码在真实数据量下必然降级：v10/EC-M 只有 213 字节

- **现象**：阶段 26 做完无后端同步后，单测与 Node harness 全绿，浏览器 gate 也过了；但截图里同步面板显示「数据较多，二维码放不下；请用同步码或同步文件」。用 `_probe.py` 量出：完整 slim 快照 346 字节 JSON，拼成 `#s=` URL **506 字节**；即使自动精简到「偏好 + 压缩目标」也有 **246 字节**，仍超上限。
- **根因**：`qrcode.js` 只实现了 QR v1–v10 / EC-M，最大 213 字节。分享图链接短（< 150 字节）所以一直没暴露；同步链接带整个冰箱/收藏/目标，任何真实用户数据都会超。此前 gate 用 `canvas 存在 or 出现降级文案` 的宽松断言，等于把缺陷放过。
- **解决**：把编码器扩到 **v1–v40 / EC-M（2331 字节）**——从 `segno` 的常量表导出 40 个版本的 `ECC_PER_BLOCK` / `NUM_BLOCKS` / `RAW_CODEWORDS` 与全部对齐图案坐标（含 v32 特例 `[6,34,60,86,112,138]`），并写脚本逐版本比对块划分；`attachBits` 的 16 位字符计数、版本信息 BCH、交织本来就与版本无关，可直接复用。`syncQRInfo()` 额外返回 `modules`，冰箱页按 `(modules+8)*3` 动态给 Canvas，避免高版本被压成 1–2 px/模块。真实数据量下现在是 **v17 / 489 字节 / 不精简**，截图二维码完整。
- **验证**：`node_qr_harness` 从 135 项扩到 412 项（40 版本全结构断言），新增 3 条 ~350 / ~910 / ~1310 字节 payload 走 `--emit` 交 `zxing-cpp` 真解码；`_browser_gate.py` 改为**严格要求 Canvas 存在且无降级文案**，并把页面实际画出的 Canvas 转 PNG 用 ZXing 解出 `#s=` 链接、再用 `syncDecode` 验出含冰箱与目标。49 项全绿。
- **沉淀**：「payload 能不能装进码」必须在**真实数据量**下验证，不能用玩具数据；宽松的 `A or 降级文案` 断言是自欺欺人。扩版本表不要手抄，找独立实现（segno）导出并逐版本对账，再用真解码器闭环。高版本符号还要同步放大渲染尺寸，否则「能生成」不等于「能扫」。

### 47. 二维码短码 magic 与压缩状态不一致，解压必崩

- **现象**：为省字节给 QR-only 同步码引入单字母 magic `Z.`，但 `syncEncode({short:true})` 无条件写入 LZ77 结果并打 `Z.`；`syncDecode()` 见到 `Z` 就 `lzDecompress()`。对小 payload（LZ77 反而膨胀）解出乱码，报「同步码已损坏，无法解析」。
- **根因**：magic 表达的是「来源」，却被同时用来推断「是否压缩」，而压缩与否是**按 payload 动态决定**的。
- **解决**：压缩状态显式分开——`Z.` = QR-only 压缩、`R.` = QR-only 原始；非短码仍是 `S1Z.` / `S1.`。编码器先比较 `packed.length < raw.length` 再选 magic，解码器只对 `S1Z` / `Z` 解压。UI 导入占位符同步改为「S1. / S1Z. / Z. / R.」，harness 对 `R.` / `Z.` 各加一条往返断言。
- **沉淀**：前缀/标志位要么完整描述编码状态，要么另设状态位；「看前缀猜格式」在有多种分支时一定会漏。新增 magic 必须同时更新解码、UI 文案和回归断言。

### 48. 公开数据集导入：别把第三方数据塞进基础语料

- **现象**：`run.py data` 会从策展规格**重建** `base_recipes.jsonl`；若把导入结果写进同一文件，下次重建就被清空；而直接把外部菜谱打进构建产物又带来许可证不清的问题。
- **根因**：人工策展与第三方导入的生命周期、来源、许可证都不同，却共用一个文件。
- **解决**：新增独立分片 `data/curated/imported_recipes.jsonl`，`load_shipped_recipes()` 按 id / title 去重后合并，`build.py` 与 `audit.py` 统一改读合并语料；导入强制显式 `--dataset` / `--license`、白名单归一化 + 受控词表校验、`--dry-run`、未知食材写待审报告。仓库只保留 3 条自写格式样例，**不捆绑任何第三方数据**。
- **沉淀**：外部数据接入先分清「源数据 / 生成数据 / 导入数据」三层，导入层永远独立可删；许可证与来源必须随记录落盘，不能靠 README 一句话。

### 49. 离线规则补齐的卡片不能冒充 AI 实测

- **现象**：新增 15 道菜后，详情页「这个变体还没预生成」按钮变成死路；用离线模板补齐很方便，但卡片会沿用「AI 创意菜，未经过人工实测」的免责声明。
- **根因**：补齐逻辑与展示层共用同一个 `source` 字段，且旧缓存与规则卡片混在一起。
- **解决**：`run.py enrich` **只补缺失条目**、绝不覆盖已有 AI 缓存；规则卡片 `source` 写死「规则生成（离线模板，非 AI 实测）」，`page-wildcard.js` 按 `source` 切换标签与免责声明。变体 1365 → 1470、ideas 195 → 210，AI 缓存零改写。
- **沉淀**：内容来源是可审计属性，不是文案细节；批量补齐必须幂等且不得覆盖成本更高、来源不同的既有内容。

### 50. `run.py build` 偶发 `shutil.rmtree` 被安全删除机制拦截

- **现象**：本机一次构建报 `OSError: [safe-delete] 操作失败: ... ERROR ...\site\js: Error during a 'trash' operation: Some operations were aborted`，此时 `site/css` 已被删、`site/js` 还在，构建处于半完成状态。
- **根因**：`copy_web_assets()` 会先 `shutil.rmtree(site/css, site/js)`；本机 Python 的 `sitecustomize` 把 `rmtree` 改成「移入回收站」，Windows 回收站偶发失败（与代码无关，也不是文件被预览服务占用——`netstat` 确认监听端口属于 WorkBuddy 主进程）。
- **解决**：**原样重跑一次 `run.py build` 即成功**；`copy_web_assets` 已有的 `_retry` 覆盖复制阶段。交付前用哈希脚本比对 `web/ ↔ site/` 全部 36 个资产、确认 `site/sw.js` 缓存版本已更新，避免把半成品当成品。
- **沉淀**：构建脚本的删除阶段是环境敏感点；遇到 trash/safe-delete 报错先重跑并核对产物完整性，不要急着重构构建逻辑或去 kill 进程。

### 51. 把「超长 URL 降级」测试从 400 字节改成 3000 字节

- **现象**：QR 扩到 v40 后，`node_share_harness` 的 `overlong QR url does not break card` 挂了——它用 `"a".repeat(400)` 造超长 URL，指望 `drawQR` 抛错走降级分支。
- **根因**：400 字节在新容量下**本就应该成功**，测试把「实现上限」当成了「期望行为」。
- **解决**：降级用例改 `repeat(3000)`（> 2331 上限），并新增一条 `medium-length URL still gets a QR` 断言，锁住 400 字节现在能正常出码；`test_sync_consistency.py` 的 `qrVersion <= 10` 同步改为 `<= 40`。
- **沉淀**：提升容量/上限后，凡是靠「触发溢出」来测降级的用例都要重新选阈值，并补一条「原本溢出的输入现在应成功」的正向回归，否则容易把能力提升误判成回归。
