# 部署说明（含预压缩配置）

`python run.py build` 产出 `site/`，纯静态，扔到任何静态主机都能跑。构建同时给每个
≥1KB 的文本资产（html/css/js/json/svg/webmanifest）产出 `.gz`（必定）与 `.br`
（装了 `Brotli` 包时）的预压缩兄弟文件，整体省 ~89% 传输字节（boot bundle
33.6KB→11.3KB gz，core.json 94KB→13.5KB br）。

本地预览（与生产同语义，按 `Accept-Encoding` 协商）：

```bash
python run.py serve --port 8000
```

## 各主机怎么配

| 主机 | 配置 |
|---|---|
| Nginx | `gzip_static on;` +（编译了 brotli 模块时）`brotli_static on;`，直接吃构建产物，零运行时 CPU |
| Caddy | 默认就预压缩+协商（`file_server` 自动用 `.gz`/`.br` 兄弟文件），不用配 |
| Netlify / Cloudflare Pages / Vercel | 平台边缘自动压缩（忽略 `.gz` 文件也没关系），零配置 |
| GitHub Pages | 已内置 `.github/workflows/pages.yml` 自动部署：推送 `main` → 测试/审计/构建 → 发布 `site/`；一次性在 Settings → Pages 把 Source 设为 GitHub Actions。其 CDN 会对文本资产做 gzip；把 `.gz`/`.br` 一并上传无害（只是多占仓库体积） |
| 任何裸静态文件服务器 | 用 `run.py serve` 同款逻辑：有 `.br`/`.gz` 且客户端接受就回 `Content-Encoding`，否则回原始文件 |

## 子路径部署（GitHub Pages 项目站点等）

项目站点会把站点挂到 `https://<user>.github.io/<repo>/` 这种前缀下。本站在前缀下
**无需任何改动**——全部资产引用、fetch、SW 注册与作用域、manifest 的
`start_url`/`scope`/图标、分享链接、日历订阅 URL 都是相对路径或按页面位置推导，
前缀天然携带。本地按真实布局验收：

```bash
python run.py serve --prefix cookmyfridge
# 打开 http://127.0.0.1:8000/cookmyfridge/
```

自动验收：`python tests/browser_stage40.py`（18 项：挂载语义、九页资源零 404、
SW 作用域、离线深链、calendar.ics 虚拟端点、manifest 图标、分享与订阅链接）。

给后来者的护栏：

- **不要引入任何以 `/` 开头的站内路径**（`href="/..."`、`fetch("/data/...")`、
  manifest 里的绝对 src）——根路径本地测试永远测不出，stage40 会在前缀下抓红。
- Service Worker 用 `register("sw.js")`（相对路径），作用域自动落在前缀内；
  不要写成 `/sw.js`。
- 用户站点（`username.github.io`）与自定义域名都是根路径部署，本节不适用。

## 必配项（与压缩无关但影响正确性）

- **Cache-Control**：HTML 与 `sw.js` 必须短缓存（`no-cache`），数据与 JS 资产可长缓存——
  站点靠 sw.js 的 `cmf-cache-<时间戳>` 版本号做整站失效，每次构建版本号自动翻滚。
- **Service Worker 作用域**：`sw.js` 必须在部署根路径可访问（子路径部署时即
  `/<前缀>/sw.js`），作用域才能覆盖整站。
- **SPA fallback 不需要**：每页都是真实 HTML 文件，深链（如 `recipe.html?id=r001`）天然可用。

## 运维注意

- Service Worker 的预缓存通过 Cache API 存储**解压后**的字节，`Content-Encoding` 对它透明，
  无需特殊处理。
- `.gz` 用 `mtime=0` 生成，字节级可复现——同一源码重复构建不会让部署 diff 出现压缩噪声。
- 修改文本资产后必须重新 `run.py build`：`.gz`/`.br` 不会自动跟进源文件的后续手改。
